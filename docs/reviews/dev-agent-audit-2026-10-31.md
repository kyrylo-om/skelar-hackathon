# Перевірка агентів та їхніх інструкцій у dev

Дата: 2026-10-31. Репозиторій: `skelar-hackathon`, гілка `dev`, HEAD `87826ad`.
На початку роботи дерево було чисте; локальний `origin/dev` указував на той самий коміт.
`git fetch` не виконувався, тому це не підтвердження найновішого стану сервера GitHub.

Перевірено промпти Guard, Triage, Actor, Critic, Responder, JSON-контракти, перевірку
планів, маршрутизацію оркестратора й відповідність інструкціям кореневого `AGENTS.md`.
Код застосунку, промпти, конфігурація та залежності в межах цього аудиту не змінювалися.

Середовище: Python 3.14.8. Наявний тимчасовий venv містив лише pip.
Помилка завантаження залежностей не доводить, що зафіксовані версії пакетів відсутні на PyPI.

**Межа доказовості:** offline-скрипт завантажує вибрані визначення функцій і констант
без змін із AST поточного коду. Залежності від Django, БД і провайдера підмінені явно.
Це виконані ізольовані unit-перевірки, а не запуск наявного Django suite, не end-to-end
перевірка і не оцінка того, як жива модель дотримується промптів.
Дев'ять неуспішних перевірок не означають дев'ять незалежних вразливостей.

## Відтворені проблеми

### 1. Високий пріоритет: Critic не отримує доказів, яких вимагає його промпт

У `backend/apps/security/critic.py:18` контекст замінюється на
`{"current_order": ...}`. Для cloud-storage pipeline це зазвичай `null`:
`policy_ctx()` передає `payments`, `subscriptions`, `vip`, але їх відкидають.

Водночас `prompts/critic.txt` вимагає звірити платежі, суми, джерела ідентифікаторів,
pending action та retention. Без цих даних незалежна перевірка не може виконати
власний чекліст. Це не доведений обхід серверних перевірок власності: вони є окремо.
Реальна модель може відхиляти коректні дії через відсутність доказів; mock цього не виявляє.

Виконаний тест: `test_regression_critic_receives_server_payment_evidence` — FAIL,
очікувані серверні `payments` відсутні. Слід передавати обмежений безпечний набір
доказів, а не весь довільний контекст чи секрети.

### 2. Високий пріоритет: збій Triage затримує явну передачу людині

Перші повідомлення «Хочу поговорити з людиною» та «Поверніть 99 грн» за невалідної
відповіді Triage отримують `clarify`, а не `review`. Причина:
`pipeline._triage()` переводить fallback в `unclear`, а `_run()` витрачає ліміт
уточнень. Для юридичних слів є детермінований маршрут, для цих звернень — немає.

Це суперечить вимозі AGENTS.md забезпечити передачу оператору навіть під час збою
провайдера. Відтворено двома окремими FAIL-тестами для людини та повернення.

### 3. Високий пріоритет: передача під час планування не зупиняє шлях виконання

`pipeline._run()` перевіряє pending review лише перед модельними викликами.
Після `_plan_and_gate()` повторної перевірки немає; `_apply()` також безумовно
додає відповідь AI. Lease у `gateway.turn()` починається лише на етапі виконання
і належить іншій сутності — прихованій `support.Conversation`, а не `review.Chat`.

Виконаний ізольований тест `test_regression_handoff_during_planning_stops_executor`
установлює pending review під час планування й підтверджує, що `_execute` усе одно
викликається. **Фактичну мутацію БД в цьому середовищі не перевірено.** Для неї
додано окремий Django regression test із передачею під час відповіді Actor.

Потрібні узгоджений стан handoff та перевірка версії перед мутацією і записом відповіді;
однієї ранньої перевірки review недостатньо.

### 4. Високий пріоритет: вкладений некоректний план спричиняє TypeError

`{"actions":[{"name":[],"params":{}}],"needs_clarification":null}` проходить
поверхневу схему Actor: вона перевіряє лише те, що `actions` є масивом.
Далі `validate_plan()` викликає `allowed.get([])` і падає з `TypeError` замість
контрольованого відхилення чи передачі людині.

Додатково `params: []` для `get_payments` перетворюється на `{}` через `or {}`
і приймається. Окремий прямий виклик валідатора з `priority: []` також падає;
**цей випадок раніше відсікається схемою router**, тому його не слід трактувати
як доведений зовнішній шлях до помилки HTTP.

Результат: 1 FAIL і 2 ERROR. Потрібні перевірка типу імені перед пошуком,
валідація вкладених полів і розрізнення відсутнього об'єкта та некоректного типу.

### 5. Середній пріоритет: Responder може вигадати виконане банківське повернення

`polish_is_safe()` перевіряє нові числа, довжину та список заборонених слів,
але пропускає заміну прохання натиснути підтвердження на:
«Гроші вже повернуто на ваш банківський рахунок.»

Виконаний тест — FAIL. У такій відповіді немає нових чисел, хоча вона змінює факт
і статус операції. **Типово `ORCHESTRATOR_LLM_RESPONDER=False`, тому цей ризик
активується при ввімкненні переписування.** Поточний прапорець не змінювався.

Також промпт очікує `RESULTS`, а `polish()` надсилає `draft`; інтерфейс слід узгодити.

### 6. Нижчий пріоритет: confidence не обмежено діапазоном 0–1

Схема приймає `confidence: 8`; перевірка `validate()` контролює тип, але не діапазон
і скінченність числа. Виконаний тест — FAIL. Це послаблює маршрутизацію за впевненістю,
хоча саме по собі не дає дозволу на мутацію.

## Проблеми, виявлені читанням коду; інтеграційного підтвердження немає

- **Pending cancellation після handoff.** `review.open_review()` змінює `Chat`, але
  не переводить приховану `support.Conversation` у `waiting_operator` і не скасовує
  її pending actions. `confirm_cancellation()` перевіряє саме `Conversation`.
  Додано Django-тест «запропонувати скасування → попросити людину → підтвердити
  стару дію». До його запуску блокування цього сценарію не підтверджене.
- **Загального deadline немає.** Є ліміт викликів та `LLM_TIMEOUT` для кожного
  звернення, але немає спільного 30-секундного дедлайну з обмеженням кожного виклику
  залишком часу. Час реальної моделі не вимірювався.
- **Actor має суперечливу інструкцію про підтвердження.** Промпт каже, що «yes/ok/do it»
  підтверджує pending action. За AGENTS.md підтвердженням є лише автентифікований
  endpoint. Backend endpoint збережений; обхід підтвердження текстом не доведений.
- **Actor не має потрібного контексту для retention.** `pending_action` завжди `None`,
  історія та ознака запропонованого/відхиленого retention не передаються, хоча промпт
  вимагає врахувати попередню пропозицію. Mock одразу пропонує скасування, ігноруючи
  цей пункт промпта, тому його успіх не доводить успіх живої моделі.
- **Огляд документації застарів.** `docs/agents/00_OVERVIEW.md` стверджує, що Actor,
  Triage, Responder та after-human-approval ще немає, хоча вони реалізовані.
  `10_ORCHESTRATOR.md` описує актуальніший стан. Політики `plans/billing/cancellation/refunds`
  у вигляді окремих файлів із кореневого AGENTS.md не знайдені.

Поточний стек відрізняється від початкової пропозиції: провайдер — DeepSeek або mock,
а SQLite використовується типово; PostgreSQL вибирається через `DATABASE_URL`.
Ці відмінності зафіксовані в поточному коді/документації; вони не змінювалися під час аудиту.
Gemma/Gemini live integration не перевірялася.

## Що підтверджено ізольованими тестами

Guard блокує відому ін'єкцію до модельного виклику, пропускає звичайне питання,
маскує email до передачі моделі, закривається при збої перевірки сумнівного тексту.
План відхиляє чужий payment ID, параметри ідентичності, зайві параметри,
невідомі дії та дві мутації. Невалідний JSON і невідомий вердикт не приймаються;
повтор обмежений одним, timeout Critic дає `needs_human`, ліміт викликів спільний
для повторів. Міркування Actor приховуються від Critic. Точний текст закриття
customer delimiter видаляється. Усі п'ять промптів містять JSON- та data-інструкції.
Наявний pending review зупиняє Triage, якщо він уже існує до початку ходу.

Це не доводить повної стійкості до prompt injection, коректності ORM permissions,
конкурентності PostgreSQL або дотримання інструкцій живою моделлю.

- `backend/apps/orchestrator/tests/test_instruction_regressions.py`: 5 **ще не виконаних**

- Цей звіт. Додані тести фіксують очікувану безпечну поведінку й залишаються червоними
  на виявлених дефектах; виправлення функціональності не входили в запит на аудит.

Із `backend/`:

```bash
python scripts/audit_agent_contracts.py
```

У середовищі з установленими `requirements-dev.txt` та тестовим `SECRET_KEY`:

```bash
pytest apps/security apps/orchestrator apps/support apps/review -q
```

Повний прогін цією командою не виконано: pytest у середовищі відсутній.
Статично знайдено 149 наявних функцій тестів агентів/security/orchestrator,
без урахування 5 нових Django regression-тестів; число не є результатом виконання.
PostgreSQL тести конкурентності слід виконати окремо з тестовою БД.

Під час аудиту в спільному дереві з'явилися сторонні зміни в `apps/support/services.py`,
`apps/product_mcp/` та `requirements-mcp.txt`. Їх не редагували й не відкочували;
результати цього аудиту не є перевіркою незавершеної MCP-інтеграції.

Наступний крок: узгодити handoff між двома моделями розмови, виправити контекст Critic
та вкладену валідацію, після чого виконати повний Django suite й окремий live smoke-test.
