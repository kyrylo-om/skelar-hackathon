## Проблеми, які потрібно розібрати

1. **AI eval-каталог не проходить: 17 із 31.** Запити про наступне списання, зміну тарифу й вимкнення автопродовження отримали clarify замість очікуваного execute. Запит про скасування після попередньої пропозиції отримав block. Частина інших розбіжностей стосується застарілих очікувань: автоматичний refund суперечить правилу передачі людині; блокування на конкретному рівні замість безпечної передачі оператору також рахується провалом. Ці результати не доводять виконання неавторизованих операцій. Усі сценарії використовували mock, а не live модель.
2. **Незбережений стан міграцій.** makemigrations --check --dry-run повертає 1. Django 6.1.2 очікує serialize=False для UUID primary key у Payment, Plan, Subscription, Action, Conversation, Message. Міграції не генерувалися і не змінювалися.
3. **Неповне Python-оточення.** PyYAML==6.0.3 зазначений у requirements.txt, але відсутній у .venv. Початковий повний pytest зупинився на трьох помилках імпорту. Для перевірки скопійовано саме версію 6.0.3 з уже встановленого локального пакета у /tmp/mlh-test-deps; requirements і .venv не змінювалися.

## Обмеження й адаптація середовища

- Поточна БД за замовчуванням — SQLite. PostgreSQL concurrency-тести пропущені; row locking і конкурентне виконання на PostgreSQL не підтверджені.
- Стандартний Starlette TestClient зависає у anyio thread portal. Для перевірки маршрутів використано тимчасовий pytest plugin, який надсилає запити безпосередньо у ASGI через httpx.ASGITransport. Код застосунку та assertions не змінювалися. Це не перевіряє мережевий HTTP, thread portal і lifecycle сервера.
- Execution HTTP-тести заблоковані забороною TCP sockets у sandbox. Повний browser E2E не запускався.
- Встановлення залежностей widget не вдалося: offline-кеш не містить playwright-core, online npm завершується EAI_AGAIN. Unit-тести та Vite-збірки widget виконані в /tmp/mlh-widget-check із залежностями frontend; повний lockfile widget не перевірено.
- Live Gemma/Gemini/DeepSeek API не викликався. Тести примусово використовують mock provider.
- Усі повторні прогони рахуються окремо; наведені числа не підсумовують ті самі тести двічі.
