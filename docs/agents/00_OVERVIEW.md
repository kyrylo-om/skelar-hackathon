# 00. Огляд конвеєра та інваріантів

Статус: чернетка. Пункти з позначкою **[узгодити]** ще не підтверджені командою.
Контекст: SupportPilot подається як B2B SaaS, шар автоматизації підтримки, який підключається до
будь-якого продукту з підпискою через **маніфест tenant-а** ([08_MANIFEST.md](08_MANIFEST.md)).
Безпека доменно-незалежна: механіка в коді, ліміти й правила в маніфесті.

Пов'язані документи: [../SECURITY_SPEC.md](../SECURITY_SPEC.md) (інтенти й маршрутизація),
[../PROMPTS.md](../PROMPTS.md) (перші версії промптів), [../ARCHITECTURE.md](../ARCHITECTURE.md).

## 1. Конвеєр: хто за ким

```
 повідомлення клієнта   (tenant_id і customer_id беруться з сесії, не з тексту)
        │
        ▼
 ┌───────────┐  block ───────────────────────────────────────────────┐
 │ 01 Guard  │  pass (masked_text)                                   │
 └─────┬─────┘                                                       │
       ▼                                                             │
 ┌───────────┐  мова, інтент, сентимент, пріоритет                   │
 │ 02 Triage │                                                       │
 └─────┬─────┘                                                       │
       ▼                                                             │
 ┌───────────┐  план дій (JSON)  ◄── контекст з API продукту         │
 │ 03 Actor  │                       (через маніфест)                │
 └─────┬─────┘                                                       │
       ▼                                                             │
 ┌───────────┐  reject → clarify (Actor переробляє, ≤ 2 рази)        │
 │ 04 Critic │  needs_human ──────────────┐                          │
 └─────┬─────┘  approve                   │                          │
       ▼                                  │                          │
 ┌───────────┐  deny ─────────────────────┼──────────────────────────┤
 │ 05 Policy │  needs_review ─────────────┤                          │
 └─────┬─────┘  allow                     ▼                          │
       │                         ┌────────────────┐                  │
       │                         │ 07 Human review│ approve →        │
       │                         │ (черга)        │ Policy ще раз    │
       │                         └───────┬────────┘                  │
       ▼                                 ▼                           │
 ┌───────────┐ ◄───────────── (після повторної перевірки)            │
 │ Executor  │  виконання дії, аудит, undo (модуль дій Кирила)       │
 └─────┬─────┘                                                       │
       ▼                                                             ▼
 ┌─────────────┐  відповідь клієнту лише з реальних результатів  ◄───┘
 │ 06 Responder│  (для block і review: шаблонна відповідь)
 └─────┬───────┘
       ▼
   QA (асинхронно): оцінка якості, метрики, дашборд   [не окремий документ]
```

`Gate` ([../../backend/apps/security/gate.py](../../backend/apps/security/gate.py)) зводить вердикти Guard,
Critic і Policy в одне рішення. Triage, Actor і Responder викликаються діалоговим кодом навколо Gate
(Андрій Киця). Executor належить Кирилу.

### Вердикти

| Компонент | Вердикти |
|---|---|
| Guard | `pass` · `block` |
| Triage | (вердикту немає, повертає класифікацію) |
| Actor | (вердикту немає, повертає план) |
| Critic | `approve` · `reject` · `needs_human` |
| Policy | `allow` · `needs_review` · `deny` |
| Human review | `approve` · `reject` |
| Gate (підсумок) | `execute` · `review` · `block` · `clarify` |

Правило зведення (найсуворіший виграє): `block` > `deny` > `needs_review` > `allow`.
Gate: будь-який `deny` дає `block`; будь-який `needs_review` дає `review`; відхилення Critic дає
`clarify` (переробити план); `needs_human` від Critic дає `review`.

### Формат trace (його малює фронтенд)

```json
{"agent": "guard|triage|actor|critic|policy|human|executor", "verdict": "...", "detail": "..."}
```

Додаткові агенти в trace (`responder`, `qa`) **[узгодити]** з фронтендом: зараз Trace.jsx знає
`guard, triage, actor, critic, policy, executor, human, qa`.

## 2. Сім непорушних інваріантів

1. **Policy Engine лише код.** Жодний вивід LLM не може змінити його рішення, і жоден промпт не має доступу
   до його правил як до чогось, що можна «домовитись» змінити.
2. **Особа береться тільки з сесії.** `tenant_id` і `customer_id` приходять із сесії або аргументу виклику, а
   не з тексту повідомлення, не з параметрів плану і не з даних, які повернув продукт.
3. **Текст клієнта це дані.** У промптах він лежить в окремому розмежованому блоці з явною забороною виконувати
   інструкції зсередини; розмежувачі з тексту вирізаються.
4. **LLM відповідає лише JSON за схемою, і збій закритий (fail closed).** Невалідний JSON, порожня відповідь або
   таймаут: один повтор, потім безпечний дефолт компонента (див. таблицю нижче). Ніколи «за замовчуванням дозволено».
5. **Найсуворіший вердикт виграє.** Порядок `block` > `deny` > `needs_review` > `allow`, без винятків.
6. **Схвалення людиною не обходить жорсткі ліміти.** Після `approve` Policy перевіряє дію ще раз у режимі
   `after_human_approval` ([05_POLICY.md](05_POLICY.md)).
7. **Кожне рішення в аудиті, пороги не захардкожені.** Аудит фіксує хто, що, коли і чому. Усі ліміти й терміни
   беруться з маніфесту tenant-а (поки в коді: з `settings.py`), а не з коду компонента.

### Безпечні дефолти при збої (fail closed)

| Компонент | Збій | Дефолт |
|---|---|---|
| Guard | LLM недоступна або невалідний JSON (для сумнівного тексту) | `block`, правило `llm_unavailable` |
| Triage | невалідний JSON / таймаут | `intent=unclear`, `confidence=0`, `priority=normal` |
| Actor | невалідний JSON / таймаут | план `escalate_to_human` |
| Critic | невалідний JSON / таймаут | `needs_human` |
| Policy | виняток у перевірці | `deny`, правило `policy_error` |
| Responder | невалідний JSON / таймаут | шаблонна відповідь за рішенням Gate |
| Executor | помилка виконання | дія не відмічена виконаною, чат передано людині |

## 3. Що в коді, що в маніфесті, що в LLM

| Питання | Код | Маніфест tenant-а | LLM |
|---|---|---|---|
| Порядок кроків конвеєра | так | | |
| Зведення вердиктів, строгість | так | | |
| Список дій продукту, їх ризик | | так | |
| Параметри дії, звідки їх брати | механіка валідації | так (схема, джерело) | пропонує значення з контексту |
| Передумови дії (власник, статус, платіж) | механіка абстрактних перевірок | мапінг на API продукту | |
| Ліміти сум, rate limit, ідемпотентність | механіка | так (числа) | |
| Хто підтверджує дію | механіка (чекає клієнта/людину) | так | |
| Розпізнавання атак | правила та маскування PII | додаткові заборонені теми | класифікує сумнівне |
| Інтент, сентимент, мова | | список інтентів і дозволені дії | визначає |
| План дій | перевірка схеми | допустимі дії для інтенту | складає |
| Відповідність плану запиту | детерміновані перевірки сум | | Critic оцінює |
| Рішення allow/deny/review | так (Policy) | параметри правил | ніколи |
| Текст відповіді клієнту | шаблони для block/review | тон, назва бренду, мова | формулює з результатів |
| Пороги ескалації | механіка лічильників | числа | |
| Аудит | так | що зберігати, термін | ніколи |
| Доступ до API продукту | клієнт HTTP, таймаути | URL, тип автентифікації, ключі (посилання на секрет) | ніколи не бачить ключів |

## 4. Порядок реалізації (що вже є в коді)

Станом на 2026-10-31 реалізовано (`backend/apps/security`, `backend/apps/orchestrator`, `backend/apps/review`):
- **Guard, Critic, Policy, Gate** (`gate_plan` і `screen_input`), LLM-адаптер з mock-режимом і DeepSeek, `router.py`
  з промптами для п'яти ролей (Guard, Triage, Actor, Critic, Responder).
- **Оркестратор** (`pipeline.py`): Triage, Actor, Responder підключені до чату клієнта, перевірка плану
  (`plan.py`), шлюз до продукту (`gateway.py`), режим `after_human_approval`, добовий ліміт повернень, перевірка
  підтвердженого платежу, історія розмови для агентів, загальний дедлайн 30 с на повідомлення.
- Детальний опис: [10_ORCHESTRATOR.md](10_ORCHESTRATOR.md).

Ще немає: читання реєстру дій і порогів з маніфесту (реєстр у `policy.py`, маніфест у `manifest.py` як Python), окремі
політики-файли `plans/billing/cancellation/refunds`, підключення MCP-мок-продуктів, QA-метрики. Те, що описано в
наступних файлах і відрізняється від коду, позначене **[узгодити]**.

## 6. Відкриті питання

1. Чи Triage і Actor окремі LLM-виклики, чи один виклик із двома контрактами (в `ARCHITECTURE.md` об'єднані).
2. Додаткові агенти в trace (`responder`, `qa`) і зміна `Trace.jsx`.
3. Бюджет часу по кроках у межах загальних 30 секунд для AI (з `docs/BACKEND.md` у гілці `dev`).
4. Де живе маніфест: файл у репозиторії, таблиця БД чи адмінка tenant-а.
5. Чи Critic працює на іншій моделі, ніж Actor.
