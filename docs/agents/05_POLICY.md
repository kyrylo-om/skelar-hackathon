# 05. Policy Engine: детермінований рушій правил

Статус: чернетка. **[узгодити]** позначає пункти без підтвердження команди.
Реалізація: `backend/apps/security/policy.py` (поточний код; режим `after_human_approval`, `payment_confirmed`,
`user_exists`, добові ліміти й читання правил з маніфесту ще не реалізовані).

> **Це не агент.** Тут немає LLM, немає системного промпта і немає «переконання». Жоден текст клієнта,
> жодна відповідь моделі й жоден коментар оператора не змінюють результат, окрім як через дані, які Policy
> перевіряє за правилами.

## Призначення
Закриває проблему «модель може помилитись або піддатись маніпуляції»: остаточно вирішує, чи можна виконати
конкретну дію для конкретного клієнта, незалежно від того, що запропонували й схвалили LLM-агенти.

## Місце в конвеєрі
- **Вхід:** `customer_id` із сесії, назва дії, параметри, контекст (факти про об'єкти клієнта), режим.
- **Вихід:** `allow` / `needs_review` / `deny` з назвою правила та причиною.
- **Викликає:** `gate()` для кожної дії плану; **ще раз** сервіс людської перевірки після `approve`
  ([07_HUMAN_REVIEW.md](07_HUMAN_REVIEW.md)).
- Записує виконані дії (`record`) для rate limit, ідемпотентності й добових сум.

## Контракт

```python
def evaluate(customer_id: int, action: str, params: dict, ctx: dict | None = None,
             mode: str = "normal") -> PolicyResult      # mode: "normal" | "after_human_approval"
def record(customer_id: int, action: str, params: dict) -> None
```
У поточному коді параметра `mode` немає **[узгодити]**.

**Вхід**
```json
{
  "customer_id": 7,
  "action": "issue_refund",
  "params": {"payment_id": "pay_81", "amount": 300},
  "ctx": {
    "facts": {"payments": {"pay_81": {"customer_id": 7, "status": "succeeded", "amount": 6000}}},
    "vip": false
  },
  "mode": "normal"
}
```
**Вихід**
```json
{"decision": "allow | needs_review | deny", "rule": "refund_auto_limit", "reason": "Сума 300 грн вища за автоліміт"}
```
Якщо жодне правило не спрацювало: `{"decision": "allow", "rule": "ok", "reason": "Усі перевірки пройдено"}`.

## Межі
Policy **не** розуміє тексту клієнта, **не** класифікує інтентів, **не** формулює відповідей, **не** виконує дій.
Він не довіряє `ctx`, отриманому від моделі: факти збирає backend із продукту через маніфест. Він не
дозволяє «виняток за проханням». Єдиний спосіб послабити правило: змінити числа в маніфесті tenant-а.

## Алгоритм
1. Для кожної дії виконати всі перевірки по порядку нижче. Кожна повертає `None` або `PolicyResult` (`deny`/`needs_review`).
2. Перевірки 1 і 2 при провалі зупиняють решту (далі немає на що спиратись).
3. Підсумок: **найсуворіший** результат (`deny` > `needs_review` > `allow`); серед рівних перший за порядком.
4. Виняток всередині перевірки: `deny`, правило `policy_error` (fail closed).

## Повна таблиця правил

| № | Назва | Умова спрацювання | Рішення | Текст для trace |
|---|---|---|---|---|
| 1 | `action_registered` (код: `unknown_action`) | дії немає в `actions` маніфесту | deny | «Дія {name} не дозволена» |
| 2 | `params_valid` (код: `invalid_params`) | немає обов'язкового параметра, невірний тип, `amount` ≤ 0 або не число, зайві ключі | deny | «Параметр {name} відсутній або некоректний» |
| 3 | `user_exists` **[нове]** | клієнта немає в продукті або заблокований | deny | «Клієнта не знайдено» |
| 4 | `user_owns_resource` (код: `ownership`) | ресурс не існує або `owner ≠ customer_id` | deny | «Об'єкт не належить цьому клієнту» (однаково для чужого й неіснуючого) |
| 5 | `payment_confirmed` **[нове]** | платіж не в статусі успішного, або вже застосований/повернений | deny | «Платіж не підтверджений або вже використаний» |
| 6 | `resource_status_in` (код: `status`) | статус ресурсу не з дозволених для дії | deny | «Дія можлива лише для об'єкта зі статусом {statuses}» |
| 7a | `amount_within_limit`: перевищує ресурс (код: `amount_exceeds_order`) | `amount` > суми ресурсу | deny | «Сума більша за суму платежу/замовлення» |
| 7b | `amount_within_limit`: жорсткий ліміт (код: `refund_hard_limit`) | `amount` > `limits.hard` | deny | «Сума перевищує жорсткий ліміт {hard}» |
| 7c | `amount_within_limit`: автоліміт (код: `refund_auto_limit`) | `limits.auto` < `amount` ≤ `limits.hard` | needs_review | «Сума {amount} вища за автоліміт» |
| 8 | `daily_cumulative_limit` **[нове]** | сума виконаних за 24 год + поточна > `daily_cumulative.limit` | deny | «Перевищено добовий ліміт» |
| 9 | `rate_limit_ok` (код: `rate_limit`) | ризикових дій за годину ≥ `rate_limit.risky_actions_per_hour` | deny | «Забагато ризикових дій за годину» |
| 10 | `not_duplicate` (код: `idempotency`) | така сама дія з тими самими `params` у вікні `idempotency_window_sec` | deny | «Така сама дія вже виконувалась щойно» |
| 11a | `always_review` (код: `human_requested`) | дія в списку `always_review` (наприклад `escalate_to_human`, повернення) | needs_review | «Запит передано людині» |
| 11b | `high_risk` | ризик дії `high` і `policies.review_high_risk` | needs_review | «Дія високого ризику потребує людини» |
| 11c | `vip` | клієнт VIP і `policies.review_vip` | needs_review | «Клієнт VIP: рішення за людиною» |

Правила 7a–7c застосовуються лише до дій з параметром суми (`amount_param` у маніфесті). Назви в дужках це
поточні імена правил у коді (`policy.py`); цільові імена нейтральні щодо домену **[узгодити перейменування]**.

## Абстрактні передумови та мапінг на API продукту

Код знає лише **абстрактні** передумови. Маніфест каже, як кожну з них перевірити для конкретного продукту.

| Передумова | Що перевіряє код | Що задає маніфест |
|---|---|---|
| `user_exists` | клієнт із сесії існує і активний | `entities.user.endpoint`, `status_field`, активні статуси |
| `user_owns_resource(ref)` | поле власника ресурсу дорівнює `customer_id` | `entities.<resource>.endpoint`, `owner_field` |
| `payment_confirmed(ref)` | статус платежу з переліку успішних, прапорець «застосовано» хибний | `entities.payment.status_field`, `confirmed_statuses`, `applied_field` |
| `resource_status_in(ref, statuses)` | статус ресурсу в списку | `entities.<resource>.status_field`, список у `actions.<a>.preconditions` |
| `amount_within_limit(param)` | сума ≤ ресурсу, ≤ жорсткого, ≤ автоліміту | `actions.<a>.limits.{auto,hard}`, `amount_param`, `entities.<r>.amount_field` |
| `rate_limit_ok(scope)` | лічильник ризикових дій за годину | `policies.rate_limit.risky_actions_per_hour` |
| `not_duplicate(window)` | немає такого самого запису в журналі дій | `policies.idempotency_window_sec` |

**Принцип мапінгу.** Кожна передумова реалізована одним загальним обробником у коді. Він читає з маніфесту:
URL-шаблон (`GET /users/{customer_id}/payments/{payment_id}`), поле власника, поле статусу, поле суми. Для
SaaS-підписки `user_owns_resource(subscription)` дивиться `subscription.user_id`, для e-commerce
`user_owns_resource(order)` дивиться `order.customer_id`. Код однаковий, змінюється лише маніфест
([08_MANIFEST.md](08_MANIFEST.md)).

Факти (`ctx.facts`) збирає backend через ці ж ендпоінти **до** виклику Policy; Policy не ходить у мережу сам і не
приймає фактів від моделі.

## Режим `after_human_approval`

Викликається, коли оператор схвалив дію ([07_HUMAN_REVIEW.md](07_HUMAN_REVIEW.md)). Стан міг змінитись, а
оператор міг змінити параметри (наприклад, меншу суму), тому перевірка потрібна ще раз.

| Правило | Режим `normal` | Режим `after_human_approval` |
|---|---|---|
| 1 `action_registered` | перевіряється | **перевіряється завжди** |
| 2 `params_valid` (з правками оператора) | перевіряється | **перевіряється завжди** |
| 3 `user_exists` | перевіряється | **перевіряється завжди** |
| 4 `user_owns_resource` | перевіряється | **перевіряється завжди** |
| 5 `payment_confirmed` | перевіряється | **перевіряється завжди** (платіж міг уже бути використаний) |
| 6 `resource_status_in` | перевіряється | **перевіряється завжди** (статус міг змінитись) |
| 7a сума > ресурсу | перевіряється | **перевіряється завжди** |
| 7b жорсткий ліміт | перевіряється | **перевіряється завжди** (людина не обходить) |
| 7c автоліміт | `needs_review` | **пропускається** (саме це й підтвердила людина) |
| 8 добовий сукупний ліміт | перевіряється | **перевіряється завжди** |
| 9 rate limit | перевіряється | пропускається **[узгодити]**, рішення прийняла людина |
| 10 `not_duplicate` | перевіряється | **перевіряється завжди** (захист від подвійного кліку) |
| 11a–11c `always_review`, ризик, VIP | `needs_review` | **пропускаються** |

Результат у цьому режимі лише `allow` або `deny`; `needs_review` неможливий. `deny` означає, що виконання не
відбувається, оператор отримує причину, дія залишається в черзі як відхилена системою.

## Сукупні ліміти за добу (захист від дроблення суми)

Приклад атаки: 20 повернень по 49 грн, кожне нижче автоліміту 50 грн.
- Перед рішенням підсумовується `amount` усіх виконаних (записаних через `record`) дій цього клієнта цієї самої
  групи дій за ковзне вікно 24 години. Якщо `сума + поточна > daily_cumulative.limit`: `deny`.
- Також діє `rate_limit_ok` (кількість ризикових дій за годину) і `not_duplicate`.
- Поточна модель `ActionLog` не зберігає суму **[узгодити: додати поле `amount`]**.
- Групи дій і ліміти в маніфесті: `policies.daily_cumulative: {refund: {actions: [issue_refund], limit: 2000}}`.

## Детерміновані перевірки до/після
Policy сам повністю детермінований. До нього: схема плану вже перевірена Actor/Critic. Після: Gate зводить
результати найсуворіше, записує `record()` лише для рішення `execute`.

## Обробка помилок (fail closed)
- Виняток у будь-якому правилі, відсутній факт у `ctx` для перевірки, що його потребує: `deny` (`policy_error` або
  відповідне правило). Відсутній об'єкт і чужий об'єкт дають однакову відповідь.
- Недоступне джерело фактів (API продукту): backend не викликає Policy з неповним контекстом; дія йде в `review`
  з причиною «неможливо перевірити».
- **Безпечний дефолт Policy: `deny`.**

## Приклади (вхід → вихід)

| № | Вхід | Вихід |
|---|---|---|
| 1 | `get_subscription`, свій ресурс, статус active | `allow`, `ok` |
| 2 | `issue_refund` 30 грн за свій платіж 99 грн (при `auto=50`, `review_refund=false`) | `allow`, `ok` |
| 3 | `issue_refund` 300 грн за свій платіж 6000 | `needs_review`, `refund_auto_limit` |
| 4 | `issue_refund` 5000 грн за свій платіж 6000 (`hard=1000`) (негативний) | `deny`, `refund_hard_limit` |
| 5 | `cancel_order` для чужого замовлення (негативний) | `deny`, `ownership` |
| 6 | `cancel_order` для замовлення зі статусом `shipped` | `deny`, `status` |
| 7 | та сама дія вдруге в межах 120 с | `deny`, `idempotency` |
| 8 | 6-та ризикова дія за годину (ліміт 5) | `deny`, `rate_limit` |
| 9 | 300 грн, режим `after_human_approval`, статус платежу змінився на «повернений» | `deny`, `payment_confirmed` |
| 10 | 300 грн, режим `after_human_approval`, усе гаразд | `allow` (автоліміт пропущено) |

## Тест-кейси

| ID | Умова | Очікується |
|---|---|---|
| P-01 | невідома дія | deny `unknown_action` |
| P-02 | `amount` = −5, `true`, відсутня | deny `invalid_params` |
| P-03 | чужий і неіснуючий ресурс | однаковий deny `ownership` |
| P-04 | `cancel_order` не в `processing` | deny `status` |
| P-05 | сума 30 / 300 / 5000 | allow / needs_review / deny |
| P-06 | сума > суми замовлення | deny |
| P-07 | повтор у вікні | deny `idempotency` |
| P-08 | rate limit перевищено | deny `rate_limit` |
| P-09 | VIP, high risk, always_review | needs_review (перемикаються налаштуваннями) |
| P-10 | кілька результатів у різні сторони | найсуворіший виграє |
| P-11 | порожній `ctx` | deny |
| P-12 | `after_human_approval`: сума понад жорсткий ліміт | deny |
| P-13 | `after_human_approval`: оператор зменшив суму нижче ліміту | allow |
| P-14 | дроблення 20 × 49 грн (добовий ліміт 2000) | deny на дії, що перевищує ліміт |
| P-15 | виняток усередині правила | deny `policy_error` |
| P-16 | `mode` = невідоме значення | deny |

## Що береться з маніфесту, а що захардкожено

| Параметр | Джерело |
|---|---|
| Реєстр дій, параметри, ризик (`actions`) | **маніфест** (зараз локальний словник у `policy.py`) |
| Статуси, власник, платіж (`entities`, `preconditions`) | **маніфест** |
| `limits.auto`, `limits.hard`, `daily_cumulative`, `rate_limit`, `idempotency_window_sec` | **маніфест** (зараз `settings.py`) |
| `always_review`, `review_high_risk`, `review_vip` | **маніфест** |
| Порядок правил, найсуворіше зведення, fail closed, режими, формат результату | **код** |
| Тексти trace українською | код (шаблони) |

## Відкриті питання **[узгодити]**
1. Перейменувати правила в нейтральні (`user_owns_resource` замість `ownership` тощо) і оновити тести.
2. Додати `amount` в `ActionLog` для добових сум.
3. Чи пропускається rate limit у режимі `after_human_approval`.
4. Чи «повернення завжди через людину» (як у `dev`) задається `always_review`, чи через `limits.auto = 0`.
5. Хто збирає `ctx.facts` і як обробляються недоступні API продукту.
6. Чи VIP визначається маніфестом (поле тарифу) чи окремим списком.
